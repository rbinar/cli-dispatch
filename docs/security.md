# Security and data

[← README](../README.md)

- **Sandbox posture per backend:** only Codex's `--read-only` is a kernel-enforced OS sandbox (macOS Seatbelt / Linux bwrap+seccomp) — a genuine no-writes guarantee, no worktree required for pure analysis. DeepSeek's `--read-only` is a tool-layer restriction only. Antigravity, OpenCode, and Copilot have **no sandbox at all**. Inside a Docker container Codex's own Linux sandbox cannot start (`bwrap: No permissions to create a new namespace`, so every worker command fails); there, set `CX_SANDBOX="danger-full-access"` in the config — the container is the isolation boundary. It replaces only the default mode; `--read-only` still wins. For everything else, isolate real repo work in a git worktree — agentic mode doesn't touch the main checkout/other branches; reviewing the diff (build/test) and merging is **up to you**.
- **Keys never leave your machine:** any key lives in `~/.config/cli-dispatch/config` (0600, outside the repo) and is **never committed**. The plugin/skill never writes a key anywhere; you add it. (Codex and Antigravity normally use their own OAuth sign-in — no key in the config at all.)
- **Keys in Claude Code's plugin config (7.0.0, Claude Code 2.1.287+):** the five worker keys are *sensitive* `userConfig` fields, entered with `/plugin configure cli-dispatch@cli-dispatch` (or `claude plugin configure … --values-stdin`) and kept in Claude Code's secure store (`~/.claude/.credentials.json`, 0600, or the macOS Keychain), not in a file of this plugin; uninstalling the plugin removes them. **Removing one key:** neither the dialog nor `--values-stdin` can clear a saved key (an empty field or `""` keeps it, `null` is rejected); overwrite it with another value, or uninstall and reinstall the plugin, which removes all five. **Residual:** the dialog masks a key but shows its last 6 characters in clear, so a screen share or recording of that dialog exposes them. Never type a key into the setup pane (it has no key field) or into the chat. Only the `dispatch` tool uses these keys: it hands the dispatched backend's key to `cli-dispatch-run` in a private environment variable, and the runner exports it, under the real name, to that worker alone. `--verify` commands, the wait call and every file stay free of it, and no command line carries it (the DeepSeek launchers export the key into `claude`'s environment, never through `env(1)`'s arguments). While the run lives, the **detached child runner** (the `nohup` process `--detach` starts, not the short-lived launcher) keeps the private variable in its initial environment block, readable by the same user only (`/proc/<pid>/environ`, `ps eww`). `--verify` commands run as that same user, so a verify command could read that file too: only run verify commands you trust. Any enabled plugin that hooks `process.run` sees the variable once when the call is made, and the SessionStart hook processes receive all five keys as `CLAUDE_PLUGIN_OPTION_*` (by design: the hook only writes the flags-only status file). `/cli-dispatch:run`, the runner agent, `doctor` and `balance` never receive a plugin-config key; they read the config file, and say so when a key is set only in the plugin config (a flags-only `userconfig-status.json` records which keys are set, never a value). Only a session whose hook was given at least one `CLAUDE_PLUGIN_OPTION_*` variable (an empty one counts) rewrites that global file; a session under another profile or config dir that got none leaves it untouched.
- **Data egress:** the **prompt and code you give a worker are sent to that backend's provider** — DeepSeek, Google (Gemini/Antigravity), OpenAI (Codex), OpenRouter/OpenCode, or GitHub Copilot. Use each only if you accept that. `/cli-dispatch:balance` is read-only and sends no prompt or code: Antigravity, Codex and Copilot are read locally, while DeepSeek and OpenRouter are queried with your API key over HTTPS (the key goes in a header fed to `curl` on stdin, not in its arguments).
- **Finished sessions are capped automatically:** every worker run prunes the session root down to the newest **100 finished** sessions before it starts. This is deletion, so the limits are worth knowing: a session that is still `running` is never removed no matter how old, a session that never wrote a state at all is left alone (only `/cli-dispatch:clean` has the idle-time evidence to judge it), and any `verdict.json` / `verdict-diff.patch` is copied into `sessions/verdict-archive/` before its directory goes. Change the cap with `CLI_DISPATCH_MAX_SESSIONS=<n>`; set it to `0` to turn pruning off entirely. This is a floor, not a replacement for `/cli-dispatch:clean` — the cap does not detect stale or dead sessions.
- **GitHub CLI (`gh`) auth forwarding:** on macOS, `gh` keeps its token in the system Keychain, which sandboxed workers (Codex's `workspace-write`, DeepSeek, agy, OpenCode, Copilot) can't reach — so delegated `gh issue`/`gh pr`/`gh api` calls silently fail. When you're logged in (`gh auth token` succeeds) and haven't set `GH_TOKEN`/`GITHUB_TOKEN` yourself, the runners **export your `gh` token into the worker as `GH_TOKEN`** so its `gh` calls authenticate. Copilot also uses that token path unless `COPILOT_GITHUB_TOKEN` is set explicitly. The token can carry broad scopes (`repo`, `workflow`, even `delete_repo`) and travels into the worker sandbox / provider context; a worker steered by prompt injection (say, while reading an issue) can use it or send it anywhere. If your delegations don't need `gh`, **opt out** by setting `CLI_DISPATCH_NO_GH_TOKEN=1`. `/cli-dispatch:doctor` reports the current state.
